## Description

You may struggle to choose a portfolio project when you have too many ideas and no clear way to compare them. In this webinar, I share a repeatable way to find a project that's relevant to the roles you want. We ground the project in real company problems and keep it small enough to finish.

I focus on AI engineering roles, but you can use the same steps for other engineering and data roles.

## Topics Covered

In the webinar, we cover:

- Choosing a target domain instead of building a random project
- Researching companies through job descriptions and engineering blogs

- Finding themes shared by several companies
- Turning one problem into a realistic first version
- Selecting a technology stack that matches the target market
- Adding evaluation, monitoring, tests, and clear documentation

## Types of Portfolio Projects

Your portfolio can include four types of projects:

- Role-targeted projects: You design these projects for a specific role and domain. Research companies in that domain, identify the problems they work on, and build something that demonstrates relevant skills.
- Personal utility projects: These tools solve problems you encounter yourself. One small utility may not be a strong portfolio piece, but a collection shows that you notice problems and build practical solutions.
- Take-home assignments: Code produced for an interview assignment can become a portfolio project, especially when the assignment was unpaid. Publish it with appropriate context to demonstrate how you approach a realistic task.
- Public and community projects: Hackathon work, open-source contributions, and community projects can all become portfolio evidence. Work that other people have reviewed or used is valuable because it shows that the project serves someone beyond its creator.

## The Six-Step Project Selection Framework

Follow these steps to choose a role-targeted project:

1. Pick a domain where you want to work.
2. Find companies in that domain that hire, or have hired, for your target role.
3. Analyze their job descriptions, engineering blogs, and technical case studies.
4. Extract the problems those companies solve.
5. Find problems or themes shared by several companies.
6. Pick one problem, design a project around it, and choose a technology stack that matches what those companies use.

Choose a domain to give your research a clear direction without depending on one company or opening. When several companies share a problem, you can discuss the same project in multiple interviews.

## Turning Research Into a Project

Start with job descriptions to learn about responsibilities, team context, and expected skills. Then use engineering blogs and case studies to learn what teams have built and which practical problems they encountered.

When reviewing these sources, focus on what the company is trying to achieve rather than collecting technology names. Treat the technology stack as supporting evidence, not as the project idea.

For each candidate project, define:

- Project: what the project is about
- User: who will use it
- Input: what data or information it needs
- Output: what it produces
- Why it fits: how it relates to the target companies and role

Generate several candidates before committing. Then select a small set of technologies that the target companies use. Avoid trying to learn too many new tools in one project.

## Scoping the First Version

Your first version should run end to end with real input and produce a useful result. A small working project is stronger than an ambitious architecture that's never finished.

Keep the first version focused on one user, one problem, a clear input, and a clear output. Additional providers, architectures, and features can become later iterations or separate projects.

For an AI engineering project, include:

1. An evaluation harness that measures whether the output is useful or correct
2. Logging or monitoring so you can review the system's behavior
3. Tests that protect the core functionality
4. A README that a hiring manager can understand quickly

## README Checklist

In your project README, help a hiring manager understand these details in a minute or less:

1. What you built
2. Who it's for
3. What input it takes
4. What output it produces
5. How you evaluate whether it works
6. Why the technology choices make sense

Most people will look at the project page before reading the code. Make the project easy to understand, run, and discuss in an interview.

## Key Takeaways

Use these principles when you choose and scope your project:

- Choose a domain first and let real company problems guide project selection.
- Prefer problems shared by several companies over a narrow idea tied to one opening.
- Define the user, input, output, and value before choosing the implementation.
- Scope the first version so it can be completed and used end to end.
- Include evaluation as a core feature of an AI project.
- A concise README is often the first and most important presentation layer.
